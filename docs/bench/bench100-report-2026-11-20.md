# 100CPS × 1万通压测迭代报告：修复与根因闭环（2026-11-20）

**目标**：修复 bench10 报告（docs/bench/bench10-report-2026-11-20.md）发现的 E 系列缺陷，然后以 100CPS × 10,000 通/轮迭代压测，直到无新缺陷。
**环境**：compose 全栈（gv-core + PG + Redis + NATS 3 节点 R3 + Kamailio 6.0.1 children=32 + RTPengine + demo-gw），`WITH_NATS_RPC=1`，`load.xml` 鉴权场景，`-l 800`（SIPp 并发不限速），`-cid_str` 唯一。
**最终结果**：**媒体开 10000/10000 满分（PDD p99=5ms）**；媒体关（隔离轮）9999/10000（PDD p99=6ms）。CDR=ledger 精确平账，runaway=0、redelivered=0、duration=0 占比 0%、answer_time 覆盖 100%。

## 根因链最终定论

1. **控制面（RPC/计费/NATS）完全健康**：隔离轮证明 100CPS×10k 时 suspend=dispatch=start 严格相等、PDD p99=6ms、零积压。bill-lock RPC 档在 100CPS 下无罪。
2. **媒体面是唯一衰减源**：INVITE 路径同步 rtpengine_manage ng 往返（Windows-Docker UDP p99=699ms）× children=32 串行容量 ≈ 每秒几十次往返，100CPS 需 100+/s → 排队 → 5s fr 灭杀。与 v0.6 "BYE-200 tail = dev-host UDP" 结论同源，量级放大 2.5×（40→100CPS）。**生产裸机（LAN RTT<1ms）不受此限**；dev-host bench 用 `GVOS_MEDIA_OFF=1` 测控制面容量。
3. **rtpengine 端口生命周期**：delete 后 socket 仍由媒体不活跃超时兜底回收（60s）；稳态端口 ≈ CPS × timeout × 4/call —— 100CPS 需 24k，默认 10k 池必炸，已扩 30k。

## 已知项（未修，记录在案）

- **F-1**：Kamailio 冷启动后 ≤60s 内 gw 表空 → 首呼 503（等 GW_SYNC 广播）。修法：gv-core 启动即推一次快照。
- **F-5**：BYE 丢失通话在 gv-core 留活 10 分钟（zombie sweep 兜底），期间 Interim 每 10s 计费 + Redis 往返（实测 5.9M ops/10min）。zombie 检测依赖 RTP 活性，无媒体环境无解；生产有 RTP 时应缩短。
- **F-7**：gv-core 对 PG 断连**无重连**，一次 PG 重启即永久退出。建议 ping 失败改指数退避重试而非 os.Exit。
- SIPp 压测容器自身在连续高压下 watchdog 停摆（3000ms 阈值）：back-to-back 大轮之间留 60s+ 冷却；`-trace_err` 保留现场。
- Kamailio cfg 语法坑（本轮踩过）：无 `%` 算子、无 `>=` 比较、常量不能裸赋值给 var、共享 queue group 名会互相覆盖。
