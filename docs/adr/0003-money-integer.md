# ADR-0003:余额与计费金额定点化(int64 计费单位),弃 float64

**状态**:已接受(2026-11-19)

## 背景

`internal/account/account.go:21` `Credit float64`,费率 7 位小数第 8 位进一(`rate.roundUp7`)。**计费系统用二进制浮点存钱是结构性风险**:IEEE754 累积误差随话单量线性放大;对账"逐分零漂移"只在当前量级(6,714 行)成立;Redis 收口后 Lua 脚本内 float 运算,Go/Redis 双端浮点语义一致性又叠一层风险。

竞品参照:昆石 VOS3000 系 20 年计费无大规模漂移事故,靠的正是定点/字符串金额(用户 2026-11-19 拍板时点名"参考竞品优秀经验")。

备选项:

| 选项 | 机制 | 评价 |
|---|---|---|
| ①维持 float64 + 对账兜底 | 现状 | 上线后余额数据迁移成本永久存在 |
| ②PG NUMERIC + Go 侧定点 | Go 无原生定点,自造 decimal 依赖 | 引依赖,不如整数干净 |
| ③**int64 计费单位(定标)** | 金额全链路以最小单位整数流转 | VOS 系经验路径 |

## 决定

**全链路定点化,int64 计费单位。**

- **定标**:1 计费单位 = 1e-4 元(万分之一元,即"厘"位)。费率 7 位小数进一改为**整数进位后按 4 位小数定标输出**;若费率确需比 1e-4 更细的粒度,定标升 1e-5/1e-6,在迁移实施时一次性测算(以现有费率表全量样本决定,宁大勿小);
- **改动面**:`account.Credit/MaxDebt`、`rate` 表价格字段、`billing` 全部中间量、`pkgplan` 折扣/最低消费、CDR 金额列(PG `NUMERIC(18,4)` 保持,Go 侧 int64 进出)、Redis Lua 脚本(`INCRBY` 整数原子,天然免浮点)、对账两端;
- **API/外部契约**:HTTP 接口金额字段**仍输出十进制字符串/小数**(客户无感),定点是内部表示——`json.Number`/字符串序列化,禁止 float64 JSON 往返;
- **对账升级**:逐分零漂移从"实测"变"结构性不可能"(整数运算封闭)。

## 后果

- 实施时机:**与 redis-adoption-plan Phase 1(余额 Lua)合并为一次账本重构**——动账本前定标,后面每一步不再放大误差窗口。上线前是唯一免费窗口(无客户余额数据要迁移);
- 工作量:中(计费核心一次精确化重构,单测全量改断言,golden 话单回放对账);
- 风险:定标位数选小了未来不够(缓解:实施时全量测算费率样本);历史 PG 数据 8 条迁移里金额列已有 NUMERIC,定点换算在 migrate 时做;
- 原 `roundUp7` 语义并入整数进位;rate 包基准(133ns)重测。
